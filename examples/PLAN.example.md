# PLAN — Импорт выписок (учебный пример)

> Синтетический пример на вымышленном проекте: показать заполненный формат
> и дать линтеру материал для прогона. Исполняется по `.claude/rules/loop-protocol.md`.

## Outcome проекта

Бухгалтер закрывает месяц, не сверяя платежи вручную: импорт разносит выписку
по договорам сам, а спорные строки показывает списком с причиной сомнения.

*Роль: бухгалтер на закрытии месяца. Момент, когда outcome существует: закрыт
месяц, ручная сверка не понадобилась ни по одной строке, кроме спорных.*

## Критическая цепь (от outcome назад к сегодня)

```
Outcome     Месяц закрыт без ручной сверки, спорные строки — отдельным списком
  ↑ звено 3 Показать спорные строки с причиной сомнения (T-3.1.1)
  ↑ звено 2 ⛔ Разнести платёж по договору правилами сопоставления (T-2.1.1, T-2.2.1)
  ↑ звено 1 Разобрать файл выписки в единый вид строк (T-1.1.1)
    (сегодня)
Узкое место ⛔ сопоставление платежа с договором: единственный участок, где
             решение неоднозначно; парсинг механичен, показ — рендер над готовым
Буфер        = 50% длительности сопоставления, перед outcome
Верёвка      израсходована половина буфера И доля автоматически разнесённых строк
             на контрольной выписке всё ещё ниже целевой из замера baseline
```

**Эксплуатация ограничения:** правила сопоставления собираются на одной реальной
выписке прошлого месяца до того, как готов импорт остальных форматов.

## Порядок исполнения (не путать с критической цепью)

1. **B-1** — разбор файла (вход для узкого места).
2. **B-2 ⛔** — сопоставление.
3. **B-3** — показ спорных.

Фидеры вне цепи (`chore`/`spike`): T-1.1.2, T-2.1.2. На цепи — только `outcome`.

## B-1 — Как бухгалтер, я хочу загружать выписку любого банка, чтобы не переносить строки руками [outcome]

### M-1.1 — Единый вид строки выписки
5W+H: who: бухгалтер / what: файл банка → строки одного вида / where: слой импорта / why: без единого вида сопоставлять нечего / how: парсер + нормализация

#### T-1.1.1 — Разбор выписки в единый вид строк
- Класс: outcome
- Метки: —
- Когда: бухгалтер загрузил файл выписки
- Роль: бухгалтер
- Хочет: получить строки выписки в одном виде независимо от банка
- Чтобы: в момент загрузки строки видны в таблице и пригодны для сопоставления
- Закрывает gap: execution — форматы банков разные, единого вида нет
- DoD: `make test SUITE=import` → зелёные на контрольном файле; строки записаны
- Runtime evidence: реальная выписка прошлого месяца загружена, все строки в таблице
- Вне scope: сопоставление с договорами
- Зависит от: — | родитель: M-1.1
- Состояние: PERSIST
- Вердикт: ⚪

#### T-1.1.2 — Отклонять файл неизвестного формата с понятной причиной
- Класс: chore
- Метки: —
- Когда: загружен файл, который парсер не узнаёт
- Роль: бухгалтер
- Хочет: увидеть причину отказа вместо пустой таблицы
- Чтобы: в момент загрузки понятно, что делать дальше, а не «ничего не произошло»
- Закрывает gap: feedback — молчаливый отказ неотличим от пустой выписки
- DoD: `make test CASE=import_unknown_format` → сообщение с причиной, код ошибки
- Runtime evidence: загрузка чужого формата → сообщение на экране
- Вне scope: поддержка новых форматов
- Зависит от: T-1.1.1 | родитель: M-1.1
- Состояние: PERSIST
- Вердикт: ⚪

5W+H: who: бухгалтер / what: журнал загруженных выписок / where: слой импорта / why: без истории непонятно, что уже грузили / how: запись факта загрузки

#### T-1.2.1 — Записывать факт загрузки выписки

- Роль: бухгалтер
- Хочет: видеть, какие выписки уже загружены и когда
- Чтобы: в момент открытия журнала видно, за какой период файлы уже есть
- Закрывает gap: feedback — повторная загрузка происходит вслепую
- DoD: `make test CASE=import_history_record` → запись создана с периодом и временем
- Runtime evidence: журнал на реальных загрузках показывает обе выписки
- Вне scope: удаление записей журнала
- Зависит от: T-1.1.1 | родитель: M-1.2
- Состояние: PERSIST
- Вердикт: ⚪

#### T-1.2.2 — Показать журнал загрузок бухгалтеру
- Класс: outcome
- Метки: —
- Когда: в журнале есть хотя бы одна запись (T-1.2.1 закрыт)
- Роль: бухгалтер
- Хочет: открыть список загруженных выписок в интерфейсе
- Чтобы: в момент открытия экрана она сама отвечает на вопрос «грузили ли уже»
- Закрывает gap: feedback — журнал есть в базе, но недоступен глазами
- DoD: `make test CASE=import_history_screen` → список отрисован
- Runtime evidence: экран журнала на реальных загрузках
- Вне scope: фильтры и поиск по журналу
- Зависит от: T-1.2.1 | родитель: M-1.2
- Состояние: PERSIST

## B-2 — Как бухгалтер, я хочу чтобы платежи сами вставали к договорам, чтобы не сверять их построчно [⛔ УЗКОЕ МЕСТО · outcome]

### M-2.1 — Правила сопоставления
5W+H: who: бухгалтер / what: платёж → договор по правилам / where: слой сопоставления / why: это единственный неоднозначный участок / how: правила на реальной выписке

#### T-2.1.1 — Сопоставление платежа с договором по назначению и реквизитам
- Класс: outcome
- Метки: —
- Когда: строки выписки разобраны (T-1.1.1 закрыт)
- Роль: бухгалтер
- Хочет: чтобы однозначные платежи вставали к договорам без её участия
- Чтобы: в момент прогона однозначные строки уже разнесены, а не ждут её
- Закрывает gap: execution — сопоставления нет
- DoD: `make test SUITE=match` → зелёные; на контрольной выписке доля разнесённых
  не ниже baseline из замера T-2.1.2
- Runtime evidence: контрольная выписка прошлого месяца разнесена, доля записана
- Вне scope: спорные строки (B-3)
- Зависит от: T-1.1.1 | родитель: M-2.1
- Состояние: PERSIST
- Вердикт: ⚪

#### T-2.1.2 — Замерить долю однозначных платежей на реальной выписке
- Класс: spike
- Метки: —
- Когда: перед проектированием правил
- Роль: разработчик
- Хочет: узнать, какая доля строк сопоставима однозначно
- Чтобы: правила проектируются под измеренную реальность, а не под догадку
- Закрывает gap: knowledge — доля однозначных строк неизвестна
- DoD: `make measure-match FILE=fixtures/statement-prev-month` → доля с разбивкой по причинам неоднозначности
- Runtime evidence: таблица замера по реальной выписке в отчёте
- Вне scope: сами правила
- Зависит от: T-1.1.1 | родитель: M-2.1
- Состояние: PERSIST
- Вердикт: ⚪

### M-2.2 — Повторный прогон не ломает разнесённое
5W+H: who: бухгалтер / what: идемпотентный импорт / where: слой сопоставления / why: выписку догружают повторно / how: ключ идемпотентности

#### T-2.2.1 — Повторная загрузка не создаёт дублей разноски
- Класс: outcome
- Метки: —
- Когда: бухгалтер загрузила ту же выписку второй раз
- Роль: бухгалтер
- Хочет: чтобы повтор не удваивал разнесённые платежи
- Чтобы: в момент повторной загрузки суммы по договорам остаются прежними
- Закрывает gap: integration — повтор загрузки штатная ситуация
- DoD: `make test CASE=match_idempotent` → повтор не меняет состояние
- Runtime evidence: двойная загрузка контрольной выписки, суммы совпали
- Вне scope: частичные выписки
- Зависит от: T-2.1.1 | родитель: M-2.2
- Состояние: PERSIST
- Вердикт: ⚪

#### T-2.2.2 — Откат разноски одной загрузки
- Класс: outcome
- Метки: —
- Когда: бухгалтер заметила, что загрузила не тот файл
- Роль: бухгалтер
- Хочет: отменить разноску конкретной загрузки

- Runtime evidence: загрузка → откат → сверка сумм с исходными
- Вне scope: частичный откат отдельных строк
- Зависит от: T-2.2.1 | родитель: M-2.2
- Состояние: PERSIST

## B-3 — Как бухгалтер, я хочу видеть спорные строки списком, чтобы закрывать месяц глядя только на них [outcome]

### M-3.1 — Список спорных с причиной
5W+H: who: бухгалтер / what: спорные строки и почему они спорные / where: интерфейс / why: без причины список бесполезен / how: рендер над результатом сопоставления

#### T-3.1.1 — Показать спорные строки с причиной сомнения
- Класс: outcome
- Метки: —
- Когда: сопоставление отработало (T-2.1.1 закрыт)
- Роль: бухгалтер
- Хочет: увидеть только неоднозначные строки и причину по каждой
- Чтобы: в момент открытия экрана видно, что именно требует её решения

- DoD: `make test CASE=disputed_screen` → спорные отфильтрованы, у каждой причина
- Runtime evidence: экран на реальной выписке, у каждой спорной строки причина
- Вне scope: массовое разрешение спорных
- Зависит от: T-2.1.1 | родитель: M-3.1
- Состояние: PERSIST
- Вердикт: ⚪

#### T-3.1.2 — Разрешить спорную строку вручную
- Класс: outcome
- Метки: —
- Когда: бухгалтер выбрала договор для спорной строки
- Роль: бухгалтер

- Чтобы: в момент выбора строка перестаёт быть спорной и уходит из списка

5W+H: who: бухгалтер / what: признак «месяц закрыт» / where: интерфейс и данные / why: outcome существует только когда месяц закрыт / how: гейт по спорным строкам

#### T-3.2.1 — Запретить закрытие месяца при нерешённых спорных строках
- Класс: outcome
- Метки: —
- Когда: бухгалтер нажала «закрыть месяц» (T-3.1.2 доступен)
- Роль: бухгалтер
- Хочет: получить отказ, если остались нерешённые спорные строки
- Чтобы: в момент нажатия месяц не закрывается молча с незакрытыми строками
- Закрывает gap: integration — закрытие возможно поверх нерешённого
- DoD: `make test CASE=close_gate` → отказ с перечнем нерешённых строк
- Runtime evidence: попытка закрыть месяц с одной спорной строкой → отказ и перечень
- Вне scope: массовое разрешение спорных
- Зависит от: T-3.1.2 | родитель: M-3.2
- Состояние: PERSIST
- Вердикт: ⚪

#### T-3.2.2 — Закрыть месяц и зафиксировать итог

- Метки: —
